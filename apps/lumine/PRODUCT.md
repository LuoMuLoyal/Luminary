# Lumine 产品定义

> 药品知识工作台。桌面端（Tauri + TanStack Start），面向药品研发与药学分析场景。
>
> 2026-10-21 起草。本文只描述 Lumine 要做什么、为什么能做、以及每项能力的
> 数据依据；不含实现细节。数据以 `DrugDataBase/` 与 Lucent 的
> `medicine-knowledge.prisma` 为准。

---

## 一、定位

Lumine 是一个**只读的药品知识分析工具**。它不做诊断、不做处方、不给患者用。

它和同工作区的另外两个产品分工如下：

| 产品     | 形态       | 用户   | 回答的问题                       |
| -------- | ---------- | ------ | -------------------------------- |
| Luminous | 手机 App   | 个人   | 「我这样吃药有风险吗」           |
| Lumine   | 桌面工作台 | 分析者 | 「这批药里有什么值得注意的结构」 |
| Lucent   | 后端       | ——     | 提供药品知识层                   |

**三者的关系是数据共享、业务不共享**：Lumine 与 Luminous 都从 Lucent 取药品
知识，但 Luminous 的用户记录、提醒、建议引擎与 Lumine 无关；Lumine 的批量分析
结果也不回流到用户侧。

### 为什么是桌面端

分析工作有三个特点，浏览器和手机都不擅长：

- **批量**：一次分析几百个分子，需要本地算力
- **大屏**：图谱与结构式需要同时铺开
- **本地文件**：SDF / CSV 直接拖进来，不必上传

### 不做什么

这条边界是产品定义的一部分，不是免责声明：

| 不做                 | 原因                                           |
| -------------------- | ---------------------------------------------- |
| 模拟未上市药物的效果 | 缺药效参数，做出来无法验证（见 §八）           |
| 预测疾病走向         | 缺个体生理与纵向队列数据                       |
| 分子对接（docking）  | 需要 3D 构象与蛋白结构预处理，SDF 只有 2D 坐标 |
| 给出用药建议         | 属于 Luminous 的领域，且需要监管合规           |
| 写入药品知识         | Lumine 全程只读                                |

## 三、数据导入清单

补导入是 Lumine 部分能力的**前置条件**。本节记录每项数据该用什么结构承载。

### 承载结构的选择依据

| 结构   | 适用                                         | 不适用           |
| ------ | -------------------------------------------- | ---------------- |
| 关系表 | 需要**按字段过滤、排序、范围查询**           | 只是整体读取     |
| JsonB  | 取一个实体、看完整内容；结构层次深；覆盖率低 | 要按内部字段筛选 |
| 向量   | 需要相似度计算                               | 只是存储         |

**判断标准是查询方式，不是数据形状。** 同一份数据可能看着复杂，但只要永远
是「按 ID 取整块」，JsonB 就是对的；反之哪怕结构简单，只要要范围查询，就必须建表。

### 逐项决策

#### 专利 —— 建表

| 项                | 内容                                                              |
| ----------------- | ----------------------------------------------------------------- |
| 理由              | 专利悬崖的核心查询是「未来 N 个月内到期」，需要按到期日做范围查询 |
| 若用 JsonB 的后果 | 全表扫描 + 逐行解析 JSON，无法建索引                              |
| 关键字段          | 专利号、国别、批准日、到期日、儿科延长期                          |

**这是唯一必须建表的补导入项。**

#### 实验属性 —— 建属性表

| 项                   | 内容                                                                    |
| -------------------- | ----------------------------------------------------------------------- |
| 形态                 | 键值对列表，同一属性有**多个来源**（熔点来自 Health Canada 或某篇论文） |
| 为什么不展开成固定列 | 会丢掉来源信息，而来源是可溯源的一部分                                  |
| 为什么不整体 JsonB   | 「找出熔点 < 100°C 的药」做不到                                         |
| 表结构要点           | 实体 + 属性名 + 文本值 + **数值** + 来源                                |

**关键设计**：属性值有混合类型（`"65 °C"`、`"3.7"`、`"Soluble"`）。必须同时保留
文本值与可空的数值列——能解析成数值的填充数值列（支持比较查询），不能解析的
只留文本。**不允许为了填数值列而丢弃原文。**

#### 通路 —— JsonB

| 项       | 内容                                   |
| -------- | -------------------------------------- |
| 形态     | 一个通路包含多个药物与多个酶（多对多） |
| 覆盖     | 652 个药（3.3%）                       |
| 判断     | 建表要 3 张去支持 3.3% 的数据，不划算  |
| 读取模式 | 「这个药参与哪些通路」——按药取整块     |

#### 代谢反应链 —— JsonB

| 项       | 内容                                                        |
| -------- | ----------------------------------------------------------- |
| 形态     | 链式（A→M1→M2→M3），每步可能带催化酶                        |
| 覆盖     | 1,014 个药（5.1%）                                          |
| 特殊之处 | 中间产物是 `DBMET` 前缀的**代谢物，不是药物**，不在药物表里 |
| 判断     | 展开成表还要另造代谢物实体，且链的长度不定                  |

#### SNP 效应 —— JsonB

| 项   | 内容                                       |
| ---- | ------------------------------------------ |
| 覆盖 | 80 个药（0.4%）                            |
| 判断 | 覆盖太薄，不支持分析功能，只做「有则展示」 |

#### 分子指纹 —— 计算生成

| 项         | 内容                                        |
| ---------- | ------------------------------------------- |
| 是什么     | Morgan 指纹（2048 bit），用于结构相似性搜索 |
| 现状       | 数据库里不存在，需从 SMILES 计算            |
| 计算时机   | **导入时算一次**，运行时只做比对            |
| 计算工具   | RDKit（Python 侧，仅导入期使用）            |
| 存储       | `bit(2048)`，复用已有的 pgvector 扩展环境   |
| 相似度度量 | **Tanimoto**（分子相似性的行业标准）        |

**关于度量的一点说明**：pgvector 提供的是余弦、L2、内积、汉明距离，**都不等于
Tanimoto**。用汉明距离替代 Tanimoto 会得到不同的排序结果——为了「用上向量索引」
而换一个不准确的度量，是本末倒置。

因此指纹用 pgvector 的表存，但相似度**用 SQL 精确计算**（按位与、按位或的位计数之比）。

**性能足够**：14,622 个分子 × 2048 bit，全表比对是毫秒到几十毫秒级。
**不需要建向量索引**。当分子库增长到几十万以上、顺序扫描开始变慢时，
再考虑「先用汉明距离粗筛、再用精确 Tanimoto 重排」的两段式。

### 依赖

| 依赖               | 状态            | 用途                         |
| ------------------ | --------------- | ---------------------------- |
| pgvector           | ✅ **已启用**   | 指纹存储（`bit(2048)`）      |
| RDKit              | ❌ **需要安装** | 导入时从 SMILES 计算指纹     |
| 新数据库           | ❌ 不需要       | 全部落在现有 PostgreSQL      |
| 向量索引           | ❌ 不需要       | 数据量太小                   |
| 图数据库           | ✅ 已有 Neo4j   | 关系网络                     |
| 化学信息学运行时库 | ❌ 不需要       | 指纹导入时算好，运行时不依赖 |

**RDKit 只用于导入期。** 算完指纹后，运行时只做位运算比对，不需要任何化学库。

## 四、两个图谱

Lumine 的可视化基于两套**性质完全不同**的图谱，不能混用。

### 4.1 Semantica 本体图（英文，结构化推理）

- 载体：Neo4j
- 服务：`semantica-service`（FastAPI，端口见部署文档）
- 规模：**3,278 节点 / 211,630 边 / 21 种关系类型**
  - Drug 895、Protein 916、ATCClass 1,467
- 端点：`/health` `/schema` `/query` `/validate` `/reason` `/rules` `/provenance`
- 特性：**确定性映射，零 LLM**。同一查询永远返回同一结果
- 能力：Cypher 规则推理 + SHACL 校验 + PROV-O 哈希链溯源

边类型（实测自导出文件）：

| 边                 | 含义         |
| ------------------ | ------------ |
| `INHIBITS`         | 抑制         |
| `INDUCES`          | 诱导         |
| `SUBSTRATE_OF`     | 作为底物     |
| `ACTS_ON`          | 作用于       |
| `INTERACTS_WITH`   | 相互作用     |
| `CARRIED_BY`       | 由……载体转运 |
| `TRANSPORTED_BY`   | 由……转运     |
| `ENZYME_LINKED_TO` | 酶关联       |

### 4.2 LightRAG 中文散文图（中文，语义检索）

- 载体：LightRAG sidecar（外置镜像）
- 内容：说明书字段级语义检索 + 医学问答
- 两个 workspace：`leaflet`（说明书）、`qa`（问答）
- 特性：**有 LLM 参与建图**，结果是概率性的
- 用途：中文自然语言提问，返回证据 chunk

### 4.3 为什么必须分开

两套图谱的证据性质不同：

- Semantica 的边是**数据里写明的**，可逐条倒查
- LightRAG 的关联是**模型推断的**，只能说「相关」

**界面上必须让用户看出这个区别。** 把两者画进同一张图、用同一种样式，
等于把推断伪装成事实——这正是 Luminous 一直在避免的事。

## 五、能力清单

按「数据是否已就绪」分三档。每项都标注了数据现状，**只有标注「需补导入」的
才依赖 §三 的导入工作**。

### A 档：数据已在库或只需一次性计算，且方法成熟

#### A1. 成药性评估（Lipinski 五规则）

| 项   | 内容                                                              |
| ---- | ----------------------------------------------------------------- |
| 输入 | DrugBank ID 列表，或本地 SDF / SMILES                             |
| 输出 | 分子量、logP、氢键供体/受体数、可旋转键数、TPSA、违规项计数、判定 |
| 数据 | `DrugbankStructure`，**已含全套 JChem 字段，已入库**              |
| 依据 | Lipinski 1997 的「rule of 5」；行业通行标准                       |
| 备注 | 规则是**启发式**，不是结论。界面上要说明它只做初筛                |

JChem 直接给出了多项成药性指标，不必自己算：`jchemRuleOfFive`（违规数）、
`jchemGhoseFilter`、`jchemVeberRule`、`jchemBioavailability`、`jchemMddrLikeRule`。

**这是数据最齐、实现最简单的一项，不需要补导入。**

**为什么适合桌面端**：一次几百个分子，本地算比网络请求快得多；数据也不必上传。

#### A2. 靶点与机制（MoA）分析

| 项   | 内容                                                   |
| ---- | ------------------------------------------------------ |
| 输入 | 一个或多个 DrugBank ID                                 |
| 输出 | 靶点列表、作用方式、生物体、**每条结论的 PubMed 引用** |
| 数据 | `targets`（10,009）                                    |
| 亮点 | 引用是数据自带的，可直接展示「这条结论来自哪篇文献」   |

**这是 Lumine 最值得做的能力**：数据自带引用，天然满足可溯源要求。

#### A3. 多药靶点重叠与脱靶分析

| 项   | 内容                                           |
| ---- | ---------------------------------------------- |
| 输入 | 药物集合                                       |
| 输出 | 共同靶点、靶点谱重叠度、可能的作用叠加或冲突   |
| 数据 | `targets` + 已入库的 DrugBank 关系表           |
| 用途 | 组合用药的机制层面分析；先导化合物的选择性评估 |

#### A4. 药物相互作用扩充

| 项   | 内容                                                     |
| ---- | -------------------------------------------------------- |
| 输入 | 药物集合                                                 |
| 输出 | 相互作用对 + 机制描述                                    |
| 数据 | `drug_interactions`（4,631），**远多于现库已导入的量**   |
| 备注 | 现有 Lucent 的 risk-check 只覆盖一部分；扩充后可显著提升 |

#### A5. 交叉引用整合

| 项   | 内容                                                                       |
| ---- | -------------------------------------------------------------------------- |
| 输入 | DrugBank ID                                                                |
| 输出 | UniProt / PDB / KEGG / PubChem / ChEBI / PharmGKB / TTD / RxCUI 链接       |
| 数据 | `externalIdentifiers`（17,309，JSON 字段，**已入库**）                     |
| 补充 | 外部网页链接（RxList / PDRhealth / Drugs.com）在 `DrugbankExternalLink` 表 |
| 用途 | 把本工具接进用户已有的工作流，而不是要求他换工具                           |

**数据已就绪，不需要补导入。**

#### A6. 图谱可视化

| 项       | 内容                                                                                     |
| -------- | ---------------------------------------------------------------------------------------- |
| 输入     | 药物 ID + 展开深度（1–3 层）                                                             |
| 输出     | 药物—靶点—酶—转运体网络图，节点可点击展开                                                |
| 数据     | Semantica 图（21 万边）                                                                  |
| 已有基础 | `semantica-service/data/viz/Warfarin-Clopidogrel.json` 是现成导出样例：166 节点 / 400 边 |
| 技术     | 前端用图布局库；节点数超过约 500 需做聚合或按类型过滤                                    |

**这一项确实能做，而且数据已就绪。** 但要先解决一个设计问题：图中必须区分
「数据写明的关系」与「推断的关系」（见 §4.3）。

#### A7. 结构相似性

| 项   | 内容                                                          |
| ---- | ------------------------------------------------------------- |
| 输入 | 一个分子，或一批分子                                          |
| 输出 | 最相似的 N 个分子 + Tanimoto 相似度分数                       |
| 数据 | `structures.sdf`（14,622 个 2D 结构）+ **需预计算的分子指纹** |
| 度量 | Tanimoto（分子相似性的行业标准）                              |
| 前提 | 指纹需要在导入时从 SMILES 计算生成，见 §三                    |
| 用途 | 找结构类似物、判断化合物新颖性、辅助专利规避分析              |

**这一项有前置条件**：指纹目前不存在，需先完成计算与导入。指纹算好后，
相似度查询本身很轻。

## 六、建议的落地顺序

按「数据就绪度 × 演示价值 × 实现成本」排序：

| 序  | 能力                     | 理由                                                         |
| --- | ------------------------ | ------------------------------------------------------------ |
| 1   | A2 靶点与机制            | 数据自带 PubMed 引用，最能体现「可溯源」；实现简单           |
| 2   | A1 成药性评估            | 数据已在库（JChem 全套）；算法是标准公式；桌面端本地算有优势 |
| 3   | A6 图谱可视化            | 已有导出样例；视觉冲击最强；能展示技术深度                   |
| 4   | A5 交叉引用 + A11 同义词 | 实现极简，但让工具「能接进现有工作流」；数据已就绪           |
| 5   | A3 + A4 多药分析         | 复用 A2 的靶点数据，逻辑上是自然延伸                         |
| 6   | A9 + A10 分类与状态筛选  | 纯查询，实现简单；让用户能「浏览」而不只是「搜索」           |
| 7   | A7 + A8 结构分析         | 需先完成指纹计算（§三），之后成本不高                        |
| 8   | A12 + A13 PK 与毒性      | 需先做文本解析，且必须标注「解析所得」                       |
| 9   | B 档各项                 | 需先补导入，且要写清限制                                     |

**先做 1–3 就能形成一个可演示的完整产品。** 第 4、6 项是低成本高感知的补充。

**注意**：第 1、2、4、6 项的数据都已在库，不需要等导入。这意味着**补导入不是
开工的前置条件**——只有第 7、9 项依赖它。

## 七、图谱可视化的具体设计

这是你特别问的一项，单独展开。

### 数据已经够

`semantica-service/data/viz/Warfarin-Clopidogrel.json` 是一个现成的导出样例：
**166 节点 / 400 边**，包含 152 个 Drug 与 14 个 Protein 节点，
8 种边类型。导出格式就是前端渲染需要的形状：

```json
{
  "graph_id": "lucent-graph-export",
  "nodes": [
    {
      "id": "DB00176",
      "type": "Drug",
      "content": "Fluvoxamine",
      "properties": { "name": "...", "half_life": "...", "categories": "[...]" }
    }
  ],
  "edges": [ ... ]
}
```

节点已带 `type` 字段，可以直接映射到不同形状/颜色。

### 可视化的三种视角

| 视角             | 展示什么                                   | 用途                 |
| ---------------- | ------------------------------------------ | -------------------- |
| **药物为中心**   | 一个药 → 它的靶点/酶/转运体 → 受影响的通路 | 理解单个药的作用谱   |
| **靶点为中心**   | 一个靶点 → 作用于它的所有药                | 找同类药、判断选择性 |
| **相互作用网络** | 多个药之间的共享靶点与代谢酶竞争           | 组合用药的机制分析   |

### 必须解决的设计问题

**1. 区分「数据写明」与「模型推断」**

Semantica 的边来自数据（可倒查），LightRAG 的关联来自模型（概率性）。
两者必须用不同线型/颜色区分，并在图例中说明。混在一起就是把推断伪装成事实。

**2. 节点数量控制**

21 万条边全画出来无法阅读。策略：

- 默认展开 1 层，用户手动展开更深
- 超过约 500 节点时按类型聚合（如「12 个酶」折叠为一个节点）
- 提供按边类型过滤（只看 `INHIBITS`，或只看 `SUBSTRATE_OF`）

**3. 边的方向与语义**

8 种边类型语义不同，不能统一画成箭头：

- `INHIBITS` / `INDUCES`：药物 → 酶/靶点，有方向
- `SUBSTRATE_OF`：药物 → 酶，有方向
- `INTERACTS_WITH`：双向
- `CARRIED_BY` / `TRANSPORTED_BY`：药物 → 蛋白，有方向

**4. 性能**

前端图布局库在 500 节点以上会明显卡顿。需要：

- 布局计算放在 Web Worker，避免阻塞界面
- 或者用 Canvas / WebGL 渲染而非 SVG

### 可视化之外还能做的

图谱不只用来「看」，还能用来**发现**：

| 能力           | 说明                                                      |
| -------------- | --------------------------------------------------------- |
| 路径查询       | 「A 药和 B 药之间有没有通过某个酶产生关联」               |
| 共同邻居       | 「这两个药共享哪些靶点」——A3 的图形化版本                 |
| 子图导出       | 把当前视图导出为 JSON / 图片，用于报告                    |
| 规则推理可视化 | Semantica 的 `/reason` 端点能推出新结论，把这些结论画出来 |

最后一项值得单独说：Semantica 有 **Cypher 规则推理**能力（`/reason` 与 `/rules`），
它能在已有边的基础上**推出新边**。把这些推理结果可视化，是这个工作台
区别于普通「药物查询工具」的地方——**别人展示数据，你展示推理**。

## 八、能力边界（为什么有些事不做）

这一节记录**被明确排除**的方向及其原因，避免以后重新讨论。

### 8.1 数字孪生 / 虚拟患者模拟

曾考虑：模拟一个患者的病情走向，可设置用药、三餐、饮水、运动、睡眠。

**结论：以现有数据做不到。** 三条硬约束：

1. **缺药效参数**。模拟药物作用至少需要 Kd/Ki、半衰期、清除率、Emax/EC50、
   作用机制。未上市药物恰恰没有这些——这正是它还在研发的原因。
2. **缺个体生理数据**。肝肾功能、基因型、合并症、既往用药史都没有。
   现有 SNP 数据只覆盖 80 个药。
3. **无法验证**。要验证「某病人吃某药会怎样」，唯一方法是真给他吃。
   未上市药物做不到，所以模型永远处于未验证状态。

同类产品（Unlearn.AI 等）做的是**基于已有患者历史数据的结局预测**，
**不模拟未上市新药**。它们有药企提供的真实队列数据，我们没有。

### 8.2 分子对接

SDF 是 2D 坐标（z 轴全为 0）。对接需要 3D 构象生成 + 蛋白结构预处理 +
打分函数，这是一个独立的专业领域，不是「顺手做一下」的功能。

### 8.3 用药建议

属于 Luminous 的职责范围，且涉及医疗合规。Lumine 只呈现数据中的事实，
不给出「应该怎么做」的建议。

## 九、中文资产怎么用

中文侧有 20 万条产品目录、约 60 万条说明书行、135 万条问答。这些是 Lumine
唯一**别人没有**的东西——Causaly、BenchSci 都不覆盖中文药品数据。

可能的用法，按可行性排序：

| 用法                 | 说明                                               | 可行性                                |
| -------------------- | -------------------------------------------------- | ------------------------------------- |
| **中英对照**         | 按 DrugBank ID 展示中文说明书与英文机制并列        | 高。已有 `cn_en_mapping.parquet`      |
| **中文检索**         | 用中文名/商品名/别名搜到对应的 DrugBank 条目       | 高。`synonyms` 18,160 + 中文映射      |
| **中文说明书原文**   | 展示不良反应、禁忌、注意事项的中文原文             | 高。数据已在库（`CnMedicineLeaflet`） |
| **问答语料挖掘**     | 从 135 万问答中提取高频问题，反推真实关注点        | 中。需要分类与去重                    |
| **中英知识差异分析** | 对比中文说明书与 DrugBank 的差异（如禁忌项不一致） | 中。有价值但需要先做字段对齐          |

**第一项最值得做**：它把「中文数据」从负担变成差异化优势。
一个中国的研究者，看英文 DrugBank 要查词典，看中文说明书又拿不到结构化字段——
把两者并排放在一起，是真实存在的需求。

⚠️ 注意 `cn_en_unmappable.parquet` 的存在，说明有一部分中文条目
**无法映射**到 DrugBank。这些条目要显式标注「未匹配」，不能静默丢弃。

## 十、与 Lucent 的接口约定

Lumine 是 Lucent 药品知识层的**只读消费者**。

| 约定     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| 路径前缀 | `/api/v1/workbench/*`，与手机端的 `/api/v1/medicines/*` 分开 |
| 权限     | 只读。不写药品知识，不碰用户数据                             |
| 认证     | 沿用 Lucent 现有认证                                         |
| 数据契约 | 以 Lucent 的 OpenAPI 为准，不手工维护接口文档                |

**为什么分前缀**：两端对同一份数据的需求不同。手机端要轻量摘要（首屏快），
桌面端要全量字段（一次拿够，减少往返）。同一个接口迁就两端会两边都不好用。

**微服务迁移的影响**：Lucent 计划把 `medicine` 拆成独立服务（P3）、
`ontology` 拆出（P7）。这两个服务正好是 Lumine 的依赖，且都不含用户数据，
因此多一个客户端不需要改造。迁移期间 Lumine 会经历一次接口地址变更。

### 11.2 最近打开与收藏

两者都**跟随账号同步**，不局限于单机。

#### 同步是产品要求

| 场景                         | 仅本地   | 跟随账号 |
| ---------------------------- | -------- | -------- |
| 换一台机器                   | 全部丢失 | 自动恢复 |
| 重装系统 / 清缓存            | 全部丢失 | 自动恢复 |
| 收藏了 30 个候选药后硬盘坏了 | 全部丢失 | 自动恢复 |

收藏是**用户投入了认知成本**的数据——他写了备注、排了序、可能持续维护了几周。
把它只留在单机上，等于随时可能被一次清缓存清掉。这是数据丢失，不是习惯问题。

#### 产品约束

| 约束           | 说明                                                                    |
| -------------- | ----------------------------------------------------------------------- |
| 跟随账号       | 登录同一账号，在任何设备看到同一份收藏与最近打开                        |
| 离线可用       | 断网时仍能查看已同步的收藏；期间的操作在恢复后补上                      |
| 收藏只存引用   | 收藏指向药品/靶点本身，不复制其内容。药品知识更新后收藏看到的是最新内容 |
| 备注是必需字段 | 收藏时填写「为什么收藏」                                                |
| 单用户数据     | 不做多端实时同步，也不做冲突合并（见下）                                |

**收藏不复制实体内容**：这一点决定了它的性质。如果收藏时把药品说明书一并存下来，
那条收藏就永远停在收藏那一刻的版本，数据更新后用户看到的是过期副本。

#### 冲突策略

同一实体在两台设备被同时修改时，**最后修改的胜出**。

不做冲突合并的理由：收藏是单用户数据，多端同时编辑同一条目的概率极低，
而「备注被覆盖」的损失（几十个字）远小于为了合并而引入的复杂度。

#### 最近打开

| 项       | 设计                                             |
| -------- | ------------------------------------------------ |
| 记录什么 | 页面类型 + 实体 + 标题 + 访问时间                |
| 上限     | 保留 100 条，界面展示 20 条                      |
| 去重     | 同一实体重复访问只更新时间，不新增条目           |
| 清理     | 用户可清空；超过 90 天自动过期                   |
| 触发条件 | 页面停留超过数秒才记录，避免快速翻页产生垃圾记录 |

#### 收藏

| 项           | 设计                                 |
| ------------ | ------------------------------------ |
| 可收藏的实体 | 药物、靶点、分析结果、图谱子图       |
| 字段         | 实体 + **备注** + 排序位置 + 时间    |
| 展示         | 侧边栏「收藏」分组，按类型分组或平铺 |
| 排序         | 手动拖拽排序，顺序跟随账号同步       |
| 导入导出     | 导出为 JSON，便于迁移与备份          |

**收藏必须有备注字段。** 收藏一个药物而不写为什么收藏，一周后就想不起来——
这是收藏功能失败的最常见原因。

### 11.3 常驻搜索框

搜索框常驻在侧边栏品牌区下方，不藏在 Cmd+K 后面。

**理由**：工作台的首要动作就是「查一个东西」。分析者打开工具时，脑子里已经有
一个药名或靶点名。把它藏在快捷键后面，等于要求用户先学会一个操作才能开始工作。

#### 搜索行为

| 输入       | 行为                                                 |
| ---------- | ---------------------------------------------------- |
| 单个词     | 跨药物、靶点、适应症、同义词、中文名并行检索         |
| 多个词     | 按空格分词，全部匹配优先                             |
| 结果       | 分组展示（药物 / 靶点 / 分类 / 收藏），每组最多 5 条 |
| 空输入聚焦 | 展示最近打开                                         |
| 回车       | 跳到完整搜索结果页                                   |
| Cmd/Ctrl+K | 同时可用，聚焦到该搜索框                             |

**中文名必须在检索范围内。** 中文侧有 20 万条目录与 18,160 个同义词，
用户很可能输入中文商品名。`cn_en_mapping.parquet` 是这层的依据；
未匹配条目要显示「未匹配到 DrugBank」而非静默丢弃。

#### 空间预算

1280×800 窗口下侧边栏可用高度约 720px。搜索框约 40px，品牌区约 56px，
剩余约 620px。四组导航 + 收藏组在折叠状态下约需 400px，够用；
但**收藏条目超过约 8 条时该组需要内部滚动**。

### 11.4 图谱探索页（含推理）

单页双 tab：

| Tab      | 内容                                        | 数据来源                     |
| -------- | ------------------------------------------- | ---------------------------- |
| **探索** | 选药 → 展开关系网络 → 过滤边类型 → 导出     | Semantica `/query`           |
| **推理** | 规则列表 → 选择规则 → 运行 → 展示推出的新边 | Semantica `/rules` `/reason` |

**合并的理由**：推理的结果就是新边，应该在同一个图里高亮显示，而不是切到另一个
页面看列表。`/reason` 返回的推理结论天然要画到图上才有意义。

**视觉区分是硬要求**：

| 边来源            | 样式                           |
| ----------------- | ------------------------------ |
| 数据中的事实边    | 实线                           |
| 规则推理出的边    | 虚线 + 不同颜色                |
| LightRAG 语义关联 | 点线，且默认隐藏（需手动开启） |

图例必须说明这三种线的区别。把推断画成和数据一样，就是误导。

### 11.5 图标

侧边栏折叠成图标模式时，每个入口必须有可辨识图标。现有 98 个图标中缺三个必需的：

| 入口     | 需要           | 处理                                                                     |
| -------- | -------------- | ------------------------------------------------------------------------ |
| 结构分析 | `IconMolecule` | **新增**（tabler 有）                                                    |
| 图谱探索 | `IconNetwork`  | **新增**                                                                 |
| 单药分析 | `IconPill`     | **新增**                                                                 |
| 其余     | 复用现有       | `product` `teams` `workspace` `sparkles` `trendingDown` `adjustments` 等 |

### 11.6 路由改动

现有模板的路由是演示用的，需要整体替换：

## 十三、术语

| 术语            | 含义                                                                                          |
| --------------- | --------------------------------------------------------------------------------------------- |
| MoA             | Mechanism of Action，作用机制                                                                 |
| Lipinski 五规则 | 判断口服药物成药性的经验规则（分子量 < 500、logP < 5、氢键供体 < 5、氢键受体 < 10，违规 ≤ 1） |
| Tanimoto 相似度 | 分子指纹的相似性度量，取值 0–1                                                                |
| Murcko 骨架     | 去掉侧链后保留的环系与连接子                                                                  |
| PBPK            | 生理药代动力学模型                                                                            |
| OAG             | Ontology-Augmented Graph，本体增强图                                                          |
| PROV-O          | W3C 溯源本体，用于记录数据来源与推导链                                                        |
| SHACL           | W3C 图数据校验语言                                                                            |
